# Fact Sheet: Transport Techniques for Self-Hosted Remote-Access Tunnels over HTTPS-Only Egress

**Scope/method:** Literature-review level engineering knowledge only — no evasion instructions or product-defeat recipes. Compiled 2026-09-25 via parallel web-verified research (RFCs, IETF drafts, vendor docs, project READMEs, engineering blogs). Two items (marked below) could not be re-verified this session because the session's WebSearch budget was exhausted after the bulk of the research; they are flagged rather than asserted as fact.

**Cross-cutting synthesis (read this before the per-topic sections):**
1. **Two different adversaries get conflated in this literature.** "Look exactly like real HTTPS" protocols (REALITY, Trojan, naiveproxy, obfs4, meek, Snowflake, WebTunnel) are designed against a network-level censor that does **not** control a trusted CA on the client (ISP/national DPI). Enterprise TLS inspection is a **stronger, different** threat: the inspecting proxy holds a CA trusted by the managed endpoint, terminates TLS, and sees full plaintext regardless of how good the outer handshake's fingerprint or CDN-routing trick is. None of the topic-11/12 protocols defeat a real corporate MITM by themselves — only an explicit **second, independently-authenticated inner encryption layer riding inside an outer TLS session that is allowed to be inspected** (topic 6's pattern) survives both adversaries at once.
2. **Every UDP-dependent technique here (QUIC/H3, MASQUE, WebTransport, Hysteria2, TUIC, STUN/ICE hole punching) is an optional accelerator, never the primary transport**, in the stated environment (UDP blocked). Major NGFW vendors document blocking QUIC/UDP-443 specifically to force fallback to inspectable TLS.
3. **TCP-over-TCP meltdown** means a design must not stack a second real reliable/congestion-controlled protocol inside a real TCP tunnel; either preserve datagram semantics in the framing or accept the throughput cost.
4. **Detection is layered independently** in real deployments: URL/domain categorization, NGFW app-ID signatures, TLS/HTTP2 fingerprinting, and TLS-inspection content analysis are four separate control points run by different products. Defeating one (e.g., fronting behind a trusted CDN to dodge categorization) does not defeat the others.

## 1. WebSocket over TLS (RFC 6455) as a tunnel carrier

RFC 6455 (Dec 2011) defines WebSocket: an HTTP/1.1 `GET` with `Upgrade: websocket` that becomes, after a `101` response, a framed full-duplex byte stream over the same TCP connection. `wss://` runs this inside ordinary TLS on 443, indistinguishable at the TLS/SNI layer from normal HTTPS. RFC 6455 §4.1 explicitly specifies proxy traversal: the client should issue `CONNECT host:port` to a configured proxy and perform the WS handshake/TLS end-to-end inside that tunnel. Because the handshake is just an HTTP/1.1 request, essentially all HTTP-aware infrastructure passes it if `Upgrade`/`Connection` headers survive. Two well-documented operational failure modes: **idle timeouts** (nginx `proxy_read_timeout` defaults to 60s, AWS ALB defaults to 60s, Cloudflare enforces 100s on Free/Pro) requiring an application-level ping/pong heartbeat under the tightest timeout in the path (~25-30s is commonly recommended); and **buffering** (reverse proxies buffer full responses by default — nginx needs `proxy_buffering off`). Real-world reports also show some TLS-intercepting corporate proxies breaking WS-carried tunnels with cryptic transport errors.

**Status 2026:** ~15 years old and ubiquitous — every major browser, CDN, cloud LB, and corporate proxy vendor supports it because mainstream SaaS depends on it, making it the most reliably-permitted "looks like HTTPS" carrier. Still HTTP/1.1-semantics in the overwhelming majority of real deployments.

**Implication for tunnel design:** WSS-over-443 via HTTP CONNECT is the single most broadly compatible carrier available, but requires a sub-timeout heartbeat and must assume default buffering is on unless the operator controls the reverse proxy.

**Sources:** [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html) (§4.1 proxy/CONNECT, §3 wss, §5.1 masking) · [nginx WebSocket proxying docs](http://nginx.org/en/docs/http/websocket.html) · [websocket.org timeout troubleshooting](https://websocket.org/guides/troubleshooting/timeout/) · [websocket.org AWS ALB guide](https://websocket.org/guides/infrastructure/aws/alb/) · [Cloudflare/ALB timeout mitigation](https://smartscope.blog/en/Infrastructure/sse-timeout-mitigation-cloudflare-alb/) · [ingress-nginx#5167](https://github.com/kubernetes/ingress-nginx/issues/5167) · [websocket.org nginx buffering guide](https://websocket.org/guides/infrastructure/nginx/) · [kilospark/sidekar#6](https://github.com/kilospark/sidekar/issues/6) (TLS-intercepting proxy breaking WS tunnel) · [Cloudflare: Everybody gets WebSockets](https://blog.cloudflare.com/everybody-gets-websockets/)

## 2. HTTP/2 extended CONNECT (RFC 8441) as a multiplexed tunnel

RFC 8441 (Sept 2018) adds a `:protocol` pseudo-header to HTTP/2 CONNECT, letting a single stream (not a whole new TCP connection) bootstrap another protocol (WebSocket is the motivating case; RFC 9220 reuses the mechanism for HTTP/3; MASQUE builds on the same base). Requires `SETTINGS_ENABLE_CONNECT_PROTOCOL=1` (one-way, per spec). The resulting tunnel is opaque DATA frames on an ordinary HTTP/2 stream, inheriting flow control and multiplexing — many logical tunnels over one TLS connection. **Critically, RFC 8441 explicitly scopes extended CONNECT to origin/edge servers, not forward proxies**: a client behind a corporate proxy should use ordinary CONNECT to reach the target, then perform the extended-CONNECT bootstrap end-to-end inside that tunnel — a forward proxy never needs to understand RFC 8441 at all.

**Status 2026:** Firefox (since v65) and Chromium both implement it, but Chromium only uses it opportunistically on an already-open H2 connection and still opens fresh HTTP/1.1 connections for new `wss://` requests; real-world WS traffic still mostly rides HTTP/1.1. Server-side support is uneven: HAProxy (since 2.4, 2021) and nghttpx support it by default; Envoy supports it but had real fallback bugs; **nginx open source still does not implement RFC 8441 server-side**, and maintainers have stated they see no demand; Caddy has not implemented it, blocked on upstream Go support. In Rust, the low-level `h2` crate added extended-CONNECT support (`h2::ext::Protocol`) in **v0.3.8 (Dec 8, 2021)**, confirmed directly from its changelog — so the primitive exists, but higher-level ergonomic WS-over-HTTP/2 library support is not mainstream (Go's equivalent proposal is still open).

**Implication for tunnel design:** Useful only for reducing handshake/connection count between client and your own server (multiplexing many logical channels over one TLS connection) — it does not change forward-proxy traversal and should be layered as an optional optimization over a WS/HTTP-1.1 fallback, never the sole carrier, given inconsistent server support (notably nginx).

**Sources:** [RFC 8441](https://www.rfc-editor.org/rfc/rfc8441.html) · [Bugzilla 1434137](https://bugzilla.mozilla.org/show_bug.cgi?id=1434137) (Firefox 65) · [Bugzilla 1774572](https://bugzilla.mozilla.org/show_bug.cgi?id=1774572) · [Cloudflare community: WS still mostly HTTP/1.1](https://community.cloudflare.com/t/websocket-over-http-2/436690) · [envoyproxy/envoy#37020](https://github.com/envoyproxy/envoy/issues/37020) / [#46959](https://github.com/envoyproxy/envoy/pull/46959) · [Envoy HTTP upgrades docs](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/http/upgrades) · [nginx trac#1992](https://trac.nginx.org/nginx/ticket/1992) / [nginx/nginx#1034](https://github.com/nginx/nginx/issues/1034) · [caddyserver/caddy#5565](https://github.com/caddyserver/caddy/issues/5565) · [nghttpx HOWTO](https://nghttp2.org/documentation/nghttpx-howto.html) · [HAProxy 2.4](https://www.haproxy.com/blog/announcing-haproxy-2-4) · [hyperium/h2 CHANGELOG](https://github.com/hyperium/h2/blob/master/CHANGELOG.md) (v0.3.8, extended CONNECT, verified directly this session) · [golang/go#53209](https://github.com/golang/go/issues/53209) (Go equivalent still open)

## 3. WebSocket over HTTP/3 (RFC 9220) and MASQUE (CONNECT-UDP RFC 9298 / CONNECT-IP RFC 9484)

RFC 9220 (June 2022) is the HTTP/3 analogue of RFC 8441: WS framing over a QUIC extended-CONNECT stream. MASQUE is an IETF *framework* (not one RFC) for tunneling UDP or IP inside an HTTP connection via extended CONNECT + HTTP Datagrams (RFC 9297) + the Capsule Protocol. **RFC 9298** "Proxying UDP in HTTP" (Aug 2022) defines `connect-udp`: relay one UDP 5-tuple as HTTP Datagrams over H3 (or H2). **RFC 9484** "Proxying IP in HTTP" (Oct 2023) defines `connect-ip`: a full VPN-like capability — the proxy assigns an address/route and whole IP packets ride as HTTP datagrams, effectively a standards-track WireGuard/OpenVPN alternative inside HTTPS infrastructure. To a middlebox, all three present as an ordinary HTTP/3 (or /2) request to a normal HTTPS server on 443.

**Status 2026:** RFC 9220 is standardized but essentially **unimplemented in production** — no major browser or server ships it (per WebSocket.org's own 2026 retrospective); HTTP/1.1 WS remains dominant. MASQUE, by contrast, is **actively and widely deployed**: Cloudflare WARP made MASQUE the **default** tunnel protocol for new device profiles (replacing WireGuard), and it's the only protocol usable in WARP "Proxy mode," with post-quantum key agreement mid-rollout. Apple's iCloud Private Relay has used a two-hop MASQUE architecture since 2021 (Apple ingress + Cloudflare/Akamai/Fastly egress), with documented fallback from QUIC to HTTP/2+TLS (`mask-h2.icloud.com`) when QUIC is blocked. Open-source MASQUE implementations exist in Go, Erlang, and Rust (`hopf-masque`). On enterprise QUIC posture: Palo Alto, Fortinet, Zscaler, and Cisco all document explicit procedures to **block QUIC outright**, stated purpose being to force fallback to inspectable TLS. No methodologically transparent public statistic gives an exact "% of enterprises blocking UDP/443" — the one number found in this research (a single-author blog estimate of ~3-5% of *public* networks) is explicitly unverified/anecdotal and the same source calls enterprise rates "substantially higher and largely unmeasured." The directionally solid, well-sourced claim is that QUIC-blocking is named, documented guidance in mainstream NGFW/SWG products, so UDP/443 availability is not a safe default assumption on managed networks.

**Implication for tunnel design:** MASQUE/CONNECT-IP is real, standards-track, and deployed at massive scale (Cloudflare, Apple), but since it needs outbound UDP/443 — which major NGFW vendors explicitly document blocking — it must be an opportunistic fast path with mandatory fallback to a TCP/443-only carrier (WS or H2 CONNECT), never the sole transport; RFC 9220 (WS/H3) can be deprioritized entirely given its lack of production implementations.

**Sources:** [RFC 9220](https://www.rfc-editor.org/rfc/rfc9220.xml) · [websocket.org: Future of WebSockets](https://websocket.org/guides/future-of-websockets/) (no production RFC 9220 impl.) · [RFC 9298](https://www.rfc-editor.org/rfc/rfc9298.xml) · [RFC 9484](https://www.rfc-editor.org/rfc/rfc9484.html) · [http.dev: MASQUE explained](https://http.dev/masque) · [Cloudflare: Zero Trust WARP tunneling with a MASQUE](https://blog.cloudflare.com/zero-trust-warp-with-a-masque/) · [Cloudflare WARP protocol settings docs](https://developers.cloudflare.com/cloudflare-one/connections/connect-devices/warp/configure-warp/warp-settings/) · [Cloudflare post-quantum WARP](https://blog.cloudflare.com/post-quantum-warp/) · [Cloudflare: iCloud Private Relay](https://blog.cloudflare.com/icloud-private-relay/) · [APNIC: Apple Relay investigation](https://blog.apnic.net/2023/01/25/an-investigation-into-apples-new-relay-network/) · [smallstep: MASQUE vs VPNs](https://smallstep.com/blog/masque-relays-vs-vpns/) · [quic-go/masque-go](https://github.com/quic-go/masque-go) · [Palo Alto KB: Block QUIC](https://knowledgebase.paloaltonetworks.com/KCSArticleDetail?id=kA10g000000ClarCAC) · [Zscaler: QUIC protocol blog](https://www.zscaler.com/blogs/product-insights/quic-secure-communication-protocol-shaping-future-of-internet) · [Cisco: How to Block QUIC](https://docs.manage.security.cisco.com/cdfmc/t_how-to-block-quic-traffic.html) · [Andrew Baker blog — UNVERIFIED anecdotal estimate](https://andrewbaker.ninja/2026/05/02/quic-the-protocol-that-breaks-your-site-without-warning/) · [w3techs QUIC usage stats](https://w3techs.com/technologies/details/ce-quic)

## 4. WebTransport

W3C/IETF API + protocol giving a socket-like abstraction over HTTP/3 (primary) with an HTTP/2 fallback mapping: reliable bidirectional/unidirectional streams plus unreliable datagrams multiplexed on one connection, positioned as WebSocket's successor for latency-sensitive multi-stream use. Specified in the W3C `WebTransport` API plus IETF `draft-ietf-webtrans-http3`/`http2`. The H3 mapping uses the same extended-CONNECT/capsule/datagram machinery as MASQUE, so it fundamentally needs UDP/443 unless negotiated down to the H2 (TCP) mapping.

**Status 2026:** W3C spec is a Candidate Recommendation Snapshot (30 July 2026, CR period through at least 30 Oct 2026) — not yet finalized; IETF `draft-ietf-webtrans-http3` was still in Working Group Last Call as of March 2026. Browser support reached **Baseline** (available in every major engine) in **March 2026** when Safari shipped it at v26.4 (Chrome since v97, Edge v98, Firefox v114). Server library maturity is uneven by language: Go's `quic-go/webtransport-go` is most mature; Node.js support is immature; Rust has two actively-maintained Quinn-based options — `wtransport` (pure-Rust async, self-described as not fully production-hardened given the pre-final spec) and `web-transport-quinn` (thin wrapper, successor to a deprecated crate), plus a generic `web-transport` crate with native+WASM backends.

**Implication for tunnel design:** Cleaner multiplexed-streams-plus-datagram abstraction than reusing raw WS or H2 CONNECT, with now-broad browser support, but treat it as an optional accelerated path (needs UDP/443, pre-Recommendation spec) with the HTTP/2 mapping as the fallback to actually design for.

**Sources:** [W3C WebTransport CR](https://www.w3.org/TR/webtransport/) · [W3C news: Invites Implementations](https://www.w3.org/news/2026/w3c-invites-implementations-of-webtransport/) · [MDN WebTransport API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API) · [websocket.org Future of WebSockets](https://websocket.org/guides/future-of-websockets/) (Baseline date, WGLC status) · [caniuse: WebTransport](https://caniuse.com/webtransport) · [quic-go/webtransport-go](https://github.com/quic-go/webtransport-go) · [w3c/webtransport#439](https://github.com/w3c/webtransport/issues/439) (Node.js immaturity) · [wtransport](https://github.com/BiagioFesta/wtransport) · [web-transport-quinn](https://crates.io/crates/web-transport-quinn) · [web-transport](https://crates.io/crates/web-transport)

## 5. HTTP CONNECT proxies in enterprises

Enterprises commonly force outbound web traffic through an explicit forward proxy. Clients discover it via a PAC file, auto-discovered through **WPAD** (DHCP option 252 or `wpad` DNS + well-known path). For TLS destinations the client sends `CONNECT host:port`; the proxy either relays raw TCP or (if inspecting) terminates TLS itself (see topic 6). Auth is typically Basic, **NTLM**, or **Negotiate** (SPNEGO/Kerberos with NTLM fallback), requiring multi-round-trip `407` challenge/response, not a static header. There is no IETF-standardized env-var convention, but `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` are de facto universal (curl, Go `net/http`, Python `requests`). None of these express PAC evaluation or NTLM/Kerberos credentials, so tools needing those typically delegate to a local helper proxy (`px`, `cntlm`) exposing a plain localhost proxy.

**Status per tool, 2026 (from each tool's own docs):**
- **ngrok** — explicitly documented: honors `http_proxy` env var and a `proxy_url` config setting; supports HTTP and SOCKS5.
- **cloudflared** — Go's `ProxyFromEnvironment` nominally applies, but a 2020 GitHub issue reporting cloudflared ignores the proxy env var for its edge connection remains open; community reports mixed success. Not a documented first-class feature the way ngrok's is.
- **Tailscale** — control-plane connection to the coordination server/DERP relays runs over HTTPS/443 and honors `HTTP_PROXY`/`HTTPS_PROXY` there, but an open feature request states these vars only affect that control connection, not general exit-node/subnet-router data traffic; no built-in PAC or NTLM/Kerberos.
- **VS Code** — the core desktop app inherits Chromium's network stack (PAC, Basic/Digest/NTLM/Negotiate), well documented; but the separate Remote Tunnels extension/`code tunnel` CLI is reported to ignore proxy settings, and VS Code's own docs mark the CLI/extension proxy layer as incomplete/legacy.
- **Teleport** — cleanest documentation of the five: `tsh` and Teleport services honor `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` for CONNECT tunneling, with inline `user:password` credentials, since `tsh` 8.3.5.

**Implication for tunnel design:** Treat "proxy support" as three separable capabilities — env-var discovery, PAC evaluation, NTLM/Kerberos handshaking — since most open-source tunnel clients reliably implement only the first; real deployments end up chaining a local NTLM/Kerberos-resolving helper proxy in front of the tunnel client's own `HTTPS_PROXY`.

**Sources:** [ngrok proxy docs](https://ngrok.com/docs/using-ngrok-with/outboundProxy) · [cloudflared#170](https://github.com/cloudflare/cloudflared/issues/170) · [Tailscale connection types](https://tailscale.com/docs/reference/connection-types) · [tailscale#11053](https://github.com/tailscale/tailscale/issues/11053) · [tailscale#10235](https://github.com/tailscale/tailscale/issues/10235) · [VS Code network setup docs](https://code.visualstudio.com/docs/setup/network) · [vscode-remote-release#8209](https://github.com/microsoft/vscode-remote-release/issues/8209) · [Teleport networking reference](https://goteleport.com/docs/reference/deployment/networking/) · [Teleport tsh CLI reference](https://goteleport.com/docs/reference/cli/tsh/) · [ACM: "WPAD: Waiting Patiently for an Announced Disaster"](https://dl.acm.org/doi/10.1145/3565361) · [px (local NTLM proxy helper)](https://github.com/genotrance/px)

## 6. TLS inspection (MITM) in enterprises

TLS/SSL inspection terminates the client's outer TLS, inspects plaintext, and opens a second TLS connection to the real origin, presenting a certificate from an enterprise-internal CA pushed to managed devices. Because it substitutes the real leaf certificate, any client-side certificate/public-key **pinning rejects the connection outright** — pinning exists to detect exactly this, so vendors' own guidance is that pinned apps must be allow-listed by destination out of inspection. The peer-reviewed literature (Durumeric et al., NDSS 2017) found many intercepting middleboxes reduced cryptographic strength or skipped validation, prompting a US-CERT/CISA advisory (TA17-075A) that HTTPS-inspection products "may weaken the protections that TLS is intended to provide." The standard vendor-neutral engineering answer: stop relying on the outer TLS layer for confidentiality — let it validate normally against the **OS trust store** (so it succeeds even with an injected enterprise root) and run a second, independently-authenticated encrypted channel (Noise, WireGuard, self-issued mTLS) inside it, so the inspecting proxy sees only opaque ciphertext it can decrypt/re-encrypt at the outer shell without ever touching the inner protocol.

**Status 2026:** SSL/TLS inspection is standard marketed functionality on enterprise SWG/NGFW products (Zscaler ZIA, Netskope, Palo Alto, Fortinet all publish dedicated docs); exact fleet-wide prevalence is vendor-claimed, not independently measured, but the practice is described as pervasive. `rustls` does **not** use the OS trust store by default (the companion `webpki-roots` crate bundles a static Mozilla set instead), so **`rustls-platform-verifier`** (maintained by the rustls project itself) is needed to defer to the OS-native verifier (Windows CryptoAPI/CNG, macOS Security.framework, Android's trust manager, falling back to `rustls-native-certs` on Linux). Actively maintained into 2026 (0.7.x line), used by 1Password, Bitwarden, Signal, and rustup — now the rustls project's own recommended default over the lower-level `rustls-native-certs` crate.

**Implication for tunnel design:** Terminate the outer/carrier TLS layer normally against the OS trust store (via `rustls-platform-verifier`) so an enterprise MITM proxy can inspect it without hard-failing, and carry a second, independently-authenticated encryption layer inside it — do not rely on pinning the outer layer.

**Sources:** [Durumeric et al., NDSS 2017](https://jhalderm.com/pub/papers/interception-ndss17.pdf) · [arXiv:1809.08729 — TLS interception appliances survey](https://arxiv.org/pdf/1809.08729) · [CISA/US-CERT TA17-075A](https://www.us-cert.gov/ncas/alerts/TA17-075A) · [Zscaler: case for inspecting corporate SSL traffic](https://www.zscaler.com/blogs/company-news/making-case-inspecting-corporate-ssl-traffic) · [Zscaler ZIA SSL inspection docs](https://help.zscaler.com/zia/policies/ssl-inspection) · [Netskope SSL decryption docs](https://docs.netskope.com/en/ssl-decryption) · [rustls-platform-verifier repo](https://github.com/rustls/rustls-platform-verifier) (adopters: 1Password, Bitwarden, Signal, rustup) · [crates.io: rustls-platform-verifier](https://crates.io/crates/rustls-platform-verifier) · [rustls-native-certs](https://github.com/rustls/rustls-native-certs)

## 7. TLS client fingerprinting (JA3/JA4) and HTTP/2 fingerprinting

TLS ClientHello fields (version, cipher suites, extensions, curves) travel in cleartext, letting a passive observer fingerprint the client *library/stack* regardless of destination. **JA3** (Salesforce, 2017) concatenates five ClientHello fields and MD5-hashes them. HTTP/2 adds a second surface — SETTINGS parameters, WINDOW_UPDATE, stream priority, pseudo-header order — first formalized in Akamai's 2017 Black Hat whitepaper. **JA4** (FoxIO, 2023, same author as JA3) is the successor: sorts fields before SHA-256 hashing, making it resilient to Chrome ≥110's ClientHello field-order randomization, which broke raw JA3. JA4+ is a family (JA4/JA4S/JA4H/JA4T/JA4X). Both JA3 and JA4 are BSD-3-Clause.

**Status 2026:** `salesforce/ja3` was **archived (read-only) in May 2025**; JA3 is widely described as legacy-but-still-computed by older tooling (Zeek, Suricata), while JA4/JA4+ is what Cloudflare, Akamai, DataDome, Imperva, and F5 run in production (Cloudflare gates JA3/JA4 fields behind Enterprise Bot Management). Open-source mimicry libraries remain actively maintained: Go's **uTLS** (refraction-networking/utls) is the de facto standard, parroting specific browsers' ClientHellos byte-for-byte. In Rust: **rquest** was renamed/superseded by **wreq** (same author, "ergonomic, privacy-aware Rust HTTP client" with fine-grained TLS/HTTP2 extension control; companion `wreq-util` ships browser-device emulation templates; rquest packages are being yanked from crates.io in favor of wreq). Both build on **cloudflare/boring** (Rust bindings for BoringSSL, Chrome's OpenSSL fork, FIPS + post-quantum X25519Kyber768 support). **rama** (plabayo) is a broader modular Tokio-native network-service framework (TLS/HTTP1/HTTP2/SOCKS5/WebSocket) for building custom proxies/clients, documented as used in production.

**Implication for tunnel design:** A tunnel client on a default/naive TLS+HTTP2 stack presents a non-browser JA4/Akamai-style fingerprint that is passively distinguishable from real browser traffic even inside a valid outer TLS session, independent of port or SNI choice.

**Sources:** [Salesforce: TLS Fingerprinting with JA3](https://engineering.salesforce.com/tls-fingerprinting-with-ja3-and-ja3s-247362855967/) · [salesforce/ja3 (archived May 2025)](https://github.com/salesforce/ja3) · [FoxIO-LLC/ja4](https://github.com/FoxIO-LLC/ja4) · [FoxIO: JA4+ network fingerprinting](https://blog.foxio.io/ja4+-network-fingerprinting) · [Cloudflare: JA4 signals](https://blog.cloudflare.com/ja4-signals/) · [Cloudflare JA4 ruleset field (Enterprise-gated)](https://developers.cloudflare.com/ruleset-engine/rules-language/fields/reference/cf.bot_management.ja4/) · [Akamai HTTP/2 fingerprinting whitepaper, Black Hat 2017](https://blackhat.com/docs/eu-17/materials/eu-17-Shuster-Passive-Fingerprinting-Of-HTTP2-Clients-wp.pdf) · [refraction-networking/utls](https://github.com/refraction-networking/utls) · [0x676e67/wreq](https://github.com/0x676e67/wreq) · [cloudflare/boring](https://github.com/cloudflare/boring) · [plabayo/rama](https://github.com/plabayo/rama)

## 8. Web categorization / URL filtering of tunnel domains

Enterprise URL-filtering vendors maintain a dedicated "proxy avoidance/anonymizer" category: Palo Alto calls it **"Proxy Avoidance and Anonymizers"** (recommended-block, plus a parallel DNS Security category with default action Block since PAN-OS 10.0), Zscaler **"Proxy/Anonymizer,"** Fortinet FortiGuard **"Proxy Avoidance,"** Cisco Umbrella **"Proxy/Anonymizer"** (which has folded in DoH providers as policy). Well-known standalone tunnel-service hostnames get caught directly — FortiGuard's public, browsable Application Control database lists **ngrok itself under category "Proxy," risk 5/5**. The harder case: tunnel *subdomains* under large reputable parents (`*.trycloudflare.com`, `*.devtunnels.ms`, `*.ts.net`) — vendors cannot blanket-block the parent without breaking legitimate CDN/SaaS traffic, and ephemeral per-session subdomains rotate faster than blocklists update. Multiple 2024-2026 threat-intel writeups (Proofpoint, GuidePoint, Securonix, CSO Online) document this exact gap being actively exploited for phishing/C2 via `trycloudflare.com`.

**Status 2026:** The category reliably catches purpose-built tunnel-*provider* hostnames but is documented as structurally unable to reliably catch ephemeral CDN subdomains — called an open, unresolved problem in current threat-intel reporting. Vendors also diverge on default handling of uncategorized/unknown domains (block vs. allow vs. flagged), an explicit, separately configurable policy choice rather than a uniform default.

**Implication for tunnel design:** A self-hosted tunnel fronted by a widely-trusted CDN hostname is categorized inconsistently and harder for static URL-category policy to block outright, at the cost of sitting in the same abuse-monitoring blind spot current threat intel is actively flagging.

## 9. Application identification of tunnel protocols by NGFWs

Palo Alto's **App-ID**, Fortinet's **FortiGuard Application Control**, and Zscaler ZIA's application catalogs identify applications independent of port/protocol via signatures, protocol decoding, and heuristics. Palo Alto's own docs state App-ID assigns behavioral characteristics like "evasive," "tunnels other applications," and "prone to misuse" as risk-score inputs, and specifically treats SSH: its SSH Proxy feature can decrypt SSH sessions to detect and block port-forwarding/tunneling behavior. Palo Alto's Applipedia and Zscaler's app-catalog pages are JavaScript-rendered SPAs that could not be scraped for specific per-app entries in this research pass — only their documented general mechanism is confirmed as vendor-published fact, not specific per-tool signature listings for cloudflared/ngrok/wireguard on those two vendors specifically (FortiGuard's server-rendered catalog stood in as the directly verifiable data point).

**Implication for tunnel design:** Reusing an unmodified well-known open-source tunnel binary or protocol (ngrok, WireGuard, generic SSH port-forwarding) over port 443 does not by itself evade NGFW application identification, since major vendors already ship dedicated, high-risk-scored signatures for these specific tools, independent of port.

## 10. TCP-over-TCP meltdown

The well-documented throughput collapse when a TCP stream (or any protocol with its own reliability/congestion-control loop) is encapsulated inside another TCP connection's payload: the inner RTO/congestion window has no visibility into the outer connection's real congestion state, because the outer TCP hides loss by transparently retransmitting. Under congestion, the outer send buffer fills, inner ACKs stall, the inner TCP's own RTO fires and backs off independently — two control loops fighting rather than cooperating, producing stalls instead of graceful degradation. Canonical reference: Olaf Titz's 2001 "Why TCP Over TCP Is A Bad Idea" (widely mirrored), formalized academically in Honda et al. 2005. **WireGuard's own docs state this explicitly** as why it refuses to support TCP transport natively. The problem is orthogonal to encryption — it applies equally to plaintext SSH port-forwarding and encrypted VPN-over-HTTPS designs.

**Mitigations, as documented:** avoid a second real reliable-delivery layer (don't proxy datagram-semantics protocols through a genuine second TCP socket if avoidable); **"fake TCP" raw-socket encapsulation** — craft real TCP/IP headers to satisfy stateful firewall/NAT tracking but implement none of TCP's actual reliability state machine, so inner loss/reordering passes through unmodified (this only survives L3/L4 stateful inspection, **not** an actual L7 proxy that re-terminates TCP/TLS itself); when a real L7 forward proxy is unavoidable, accept a genuine TCP/TLS socket and instead carry UDP-semantics payloads as discrete framed messages rather than a second reliable byte stream, tuning buffers/MTU/timeouts.

**Tools:** **udp2raw** (`wangyu-/udp2raw`, C++, MIT) converts UDP into raw-socket FakeTCP/ICMP/UDP to get through stateful UDP-blocking firewalls; explicitly endorsed in WireGuard's own docs as a sanctioned external workaround. **phantun** (`dndx/phantun`, Rust, MIT-style, actively published v0.8.1) does the same in "100% safe Rust," explicitly states it targets L3/L4 firewalls only and will **not** pass an L7 proxy. **wstunnel** (`erebe/wstunnel`, Rust since a v7.0 rewrite, BSD-3-Clause, actively maintained) carries arbitrary TCP/UDP/Unix-socket traffic inside *genuine* WebSocket, HTTP/2, or WebTransport streams — unlike udp2raw/phantun it terminates real TLS/HTTP framing, so it's designed to survive real L7 forward proxies; has a documented WireGuard-over-wstunnel mode. "WireGuard over WebSocket" also exists as a general community pattern (third-party wrapper scripts, not a WireGuard built-in).

**Implication for tunnel design:** Because a real authenticated corporate proxy terminates genuine TCP/TLS (ruling out fake-TCP tools like phantun/udp2raw, which only fool L3/L4 firewalls), a tunnel meant to survive such proxies must ride inside a real WS/H2/H3 stream (à la wstunnel) and carry UDP-semantics payloads as framed messages rather than a second genuine TCP byte-stream.

**Sources:** [Wikipedia: TCP meltdown problem](https://en.wikipedia.org/wiki/TCP_meltdown_problem) · [WireGuard: known limitations (official TCP-refusal statement)](https://www.wireguard.com/known-limitations/) · [rfc1036/udptunnel](https://github.com/rfc1036/udptunnel) · [wangyu-/udp2raw](https://github.com/wangyu-/udp2raw) · [dndx/phantun](https://github.com/dndx/phantun) · [erebe/wstunnel](https://github.com/erebe/wstunnel) · [jnsgruk/wireguard-over-wss](https://github.com/jnsgruk/wireguard-over-wss) · [Honda et al. 2005, "Understanding TCP over TCP"](https://lsnl.jp/~ohsaki/papers/Honda05_ITCom.pdf)

## 11. Tor pluggable transports as prior art

Tor's PT architecture (spec v1) lets a plugin transform Tor's traffic before it hits the network. Since 2023, obfs4, meek, Snowflake, and WebTunnel are consolidated into one Go binary, **Lyrebird**, replacing the unmaintained standalone `obfs4proxy`. All four remain shipped and user-selectable in Tor Browser as of 2026.

- **obfs4** — a "look-like-nothing" obfuscation layer (descended from ScrambleSuit): full handshake every connection using Tor's ntor handshake with Elligator2-obfuscated public keys so handshake bytes are statistically indistinguishable from random, NaCl-secretbox link encryption, optional inter-arrival timing obfuscation. Still the most effective general-purpose default bridge type per Tor Project materials, but its high-entropy stream is itself a recognizable signature to entropy-analyzing DPI — the reason WebTunnel/Snowflake exist as alternatives that mimic a *specific* recognizable protocol shape instead.
- **meek (domain fronting)** — outer TLS SNI/DNS point to an allowed CDN-fronted domain while the real destination is named only in the encrypted Host header. **Degraded, not fully retired**: Google Cloud and CloudFront disabled cross-domain fronting at their routing layer in **April-May 2018**, breaking meek's two most-used configurations; still bundled in Tor Browser but positioned as the slowest, last-resort option.
- **Snowflake** — routes Tor traffic through a large, constantly-churning pool of volunteer browser-based WebRTC proxies, so an observer sees what looks like an ordinary WebRTC call rather than a fixed server IP; PT v2.1, actively developed, recommended fallback when obfs4 bridges get enumerated and blocked.
- **WebTunnel** — newest (2023), inspired by "HTTPT": the client sends what looks exactly like a normal HTTPS WebSocket Upgrade request to what appears externally to be an ordinary website (a load balancer routes the upgrade request to the WebTunnel process, everything else to the real site). Gaining adoption specifically because it targets **allow-list, deny-by-default** networks — exactly this literature review's threat model — unlike obfs4's random-looking bytes, which allow-list environments reject by default. Requires the operator to run a real front-end website, a nontrivial deployment cost versus obfs4.

**Status 2026 (adversarial reality check):** a Tor Project forum report from China (April 2025) described obfs4/meek/Snowflake as effectively unusable against the current Great Firewall, with WebTunnel connecting but being quickly blocked — a reminder this is a continuous arms race against nation-state DPI, not a solved problem (a far stronger adversary than typical enterprise TLS inspection).

**Implication for tunnel design:** WebTunnel is the closest prior art to "make an arbitrary tunnel indistinguishable from a real HTTPS/WebSocket connection under an allow-list firewall"; meek demonstrates domain fronting specifically has not been a reliable foundation since 2018; obfs4/Snowflake show the "look like nothing" vs. "look like a specific common protocol" design trade-off.

**Sources:** [Tor PT spec v1](https://spec.torproject.org/pt-spec/) · [Tor support: Lyrebird / circumvention](https://support.torproject.org/tbb/lyrebird/) · [obfs4 protocol spec](https://gitlab.torproject.org/tpo/anti-censorship/pluggable-transports/lyrebird/-/blob/HEAD/doc/obfs4-spec.txt) · [Tor Project: domain fronting and the open web](https://blog.torproject.org/domain-fronting-critical-open-web/) · [meek design / 2018 CDN shutdown](https://trac.torproject.org/projects/tor/wiki/doc/meek) · [Snowflake repo](https://gitlab.torproject.org/tpo/anti-censorship/pluggable-transports/snowflake) · [Tor Project: Introducing WebTunnel](https://blog.torproject.org/introducing-webtunnel-evading-censorship-by-hiding-in-plain-sight/) · [WebTunnel repo](https://gitlab.torproject.org/tpo/anti-censorship/pluggable-transports/webtunnel) · [Tor forum: China April 2025 GFW report](https://forum.torproject.org/t/feedback-from-china-april-2025-increased-gfw-censorship-obfs4-meek-snowflake-unusable-webtunnel-connects-but-is-quickly-blocked/18233)

## 12. Censorship-circumvention protocols as prior art

*(Note: these solve "invisible to a non-MITM-capable network censor," not "survives an enterprise proxy with a trusted decrypting CA" — see cross-cutting synthesis above.)*

**Xray VLESS + REALITY** — VLESS is a lightweight, stateless proxy protocol relying on its outer transport for encryption. REALITY eliminates the server's own TLS fingerprint: for any client not presenting a valid short-term key in the ClientHello, the server transparently forwards the TLS handshake to a real, innocuous upstream site, so active probes/passive observers see a byte-for-byte legitimate handshake with a real site's real certificate. Go, part of XTLS/Xray-core (MPL-2.0; standalone REALITY repo dual MPL-2.0/BSD-3-Clause). Very actively developed in 2026; widely regarded in the circumvention community as the current best-resistance self-hosted TCP/TLS protocol against DPI blocking, though community reports describe intermittent REALITY interference in Iran specifically. Quantitative "bypass rate" claims circulating on SEO blogs are unverified, not peer-reviewed.

**XHTTP/SplitHTTP** — Xray-core's HTTP/1.1-, H2-, H3-aware transport, positioned as the recommended replacement for WebSocket/gRPC transports (which produce persistent, statically-shaped, easier-to-fingerprint connections). Splits a logical connection into discrete HTTP request/response exchanges resembling an ordinary file download rather than a persistent tunnel. Go, MPL-2.0. Actively evolving in 2026, including ongoing work to run stably over H2 (h2c origin) behind Cloudflare Tunnel.

**Trojan** — architecturally the simplest: run a real HTTPS web server and multiplex a proxy protocol onto the *same* TLS port, distinguished only by a secret password sent as the first bytes after the handshake; non-matching connections pass through to the real site content. Resistant to active probing since the TLS handshake is completely standard. Original trojan-gfw/trojan is C++ (CMake/Boost/OpenSSL), GPLv3; release cadence has slowed (latest v1.16.0, June 2026) as the protocol has outlived the reference implementation, now commonly consumed as one protocol type inside actively-developed multi-protocol cores (Xray-core, sing-box) and Rust reimplementations.

**naiveproxy** — reuses Chromium's actual network stack client-side, so TLS ClientHello, H2 settings/frame ordering, and connection reuse are literally identical to real Chrome traffic, sidestepping JA3/JA4/H2-fingerprinting by construction rather than mimicry. Server side is typically Caddy's forwardproxy plugin (Go); the companion fork klzgrad/forwardproxy adds a naiveproxy-originated padding layer upstream Caddy lacks. Client is C++/BSD-3-Clause, server is Go. Actively maintained by a single primary author (klzgrad), client rebased onto a new Chromium root for every Chrome release — latest tracked release dated **Sept 25, 2026**, rebased to Chrome 154.

**Hysteria2** — QUIC-based proxy with custom congestion control tuned for lossy/high-latency links, Salamander-style obfuscation, and (as of the Sept 2026 release) a built-in ECH key/config subcommand. Go, MIT, under apernet/HyNetworks. Actively maintained (v2.12.3, Sept 16 2026). **Fundamentally QUIC/UDP** — requires outbound UDP by design, not directly usable under strict UDP-blocked egress without a TCP-wrapping layer. GFW Report's peer-reviewed USENIX Security 2025 paper documents China's GFW decrypting/SNI-filtering QUIC Initial packets in production since April 2024, relevant context for any QUIC-based protocol's resistance claims (not specific to Hysteria2).

**TUIC** — minimal, 0-RTT-capable proxy protocol over QUIC relaying TCP and UDP with full-cone-NAT-friendly semantics. Notable maintenance history: the original implementation (EAimTY/tuic) was archived Jan 2024; the author's own 2025 post explains the project restarted as a community effort (tuic-protocol org), refactored into protocol-spec-only (GPL-3.0-or-later spec repo) plus separate Rust crates built on `quinn`. Leading successor implementation is Itsusinn/tuic (actively developed, 900+ commits). Same UDP-only caveat as Hysteria2.

**shadowsocks-rust** — Rust reimplementation of Shadowsocks: client/server share a pre-shared key, wrap TCP/UDP in AEAD-encrypted, SOCKS5-like framing with minimal metadata; historically valued for simplicity/low overhead rather than active-probing resistance (plain Shadowsocks traffic is statistically distinguishable from TLS, part of why Trojan/REALITY moved to "look exactly like TLS" instead). MIT, actively maintained (v1.25.0, Aug 26 2026, ~11k stars). Now functions less as a standalone circumvention-of-choice and more as a well-optimized building block bundled inside multi-protocol cores.

**Implication for tunnel design:** This family shows the field has converged on two complementary patterns for TCP-443-only, DPI-inspected egress — (1) make the outer TLS handshake byte-identical to a real browser/website (REALITY, naiveproxy, Trojan) to defeat active probing/fingerprinting, and (2) shape inner traffic to resemble ordinary HTTP request/response patterns (XHTTP/SplitHTTP) to defeat traffic-pattern analysis; the QUIC-based designs (Hysteria2, TUIC) answer a *different, less constrained* threat model (UDP available) and don't directly apply to a strict UDP-blocked scenario without a TCP-wrapping layer — and **none** of the seven defeat a real corporate TLS-terminating MITM by themselves (see synthesis note at top).

**Sources:** [XTLS/Xray-core](https://github.com/XTLS/Xray-core) · [xtls/reality](https://github.com/xtls/reality) · [Xray-core#3269 — Iran field reports](https://github.com/XTLS/Xray-core/discussions/3269) · [XHTTP official docs](https://xtls.github.io/en/config/transports/splithttp.html) · [Xray-core#4113 — XHTTP design rationale](https://github.com/XTLS/Xray-core/discussions/4113) · [trojan-gfw/trojan](https://github.com/trojan-gfw/trojan) · [trojan-gfw releases (v1.16.0, June 2026)](https://github.com/trojan-gfw/trojan/releases) · [trojan protocol design doc](https://trojan-gfw.github.io/trojan/protocol.html) · [klzgrad/naiveproxy](https://github.com/klzgrad/naiveproxy) · [naiveproxy releases (Sept 25 2026, Chrome 154)](https://github.com/klzgrad/naiveproxy/releases) · [apernet/hysteria](https://github.com/apernet/hysteria) · [hysteria releases (v2.12.3)](https://github.com/apernet/hysteria/releases) · [GFW Report, USENIX Security 2025 — QUIC SNI censorship](https://gfw.report/publications/usenixsecurity25/en/) · [tuic-protocol/tuic](https://github.com/tuic-protocol/tuic) · [original author's restart post](https://www.eaimty.com/2025/restart-developing-tuic-but-not-as-the-author/) · [Itsusinn/tuic](https://github.com/Itsusinn/tuic) · [shadowsocks/shadowsocks-rust](https://github.com/shadowsocks/shadowsocks-rust) · [shadowsocks-rust releases (v1.25.0)](https://github.com/shadowsocks/shadowsocks-rust/releases)

## 13. NAT traversal fundamentals for an optional direct path

**STUN** (RFC 8489) discovers the server-reflexive `ip:port` a NAT allocated. **TURN** (RFC 8656) is the relay-of-last-resort when no direct path exists, itself runnable over TCP/TLS on 443. **ICE** (RFC 8445) orchestrates: gather candidates, exchange via signaling, probe pairs in parallel, pick the best, falling back to TURN. Plain hole punching works for easy/cone NATs but fails for hard/symmetric NATs (fresh random external port per destination). **Tailscale's engineering blog** documents a probabilistic "birthday attack" for symmetric NATs, with worked figures: 174 random probes ≈ 50% success, 256 ≈ 64%, 1024 ≈ 98%. **DCUtR** (libp2p) is the P2P-network analogue: reuses an already-established relayed connection purely as the signaling channel to coordinate a synchronized hole punch, avoiding a separate STUN/ICE-style server.

**Status 2026:** STUN/TURN/ICE are mature, widely deployed via WebRTC; DCUtR is production in libp2p/IPFS and iroh (a QUIC-based P2P library adopting an emerging IETF "QNT" approach). Published figures: Tailscale states direct P2P connections succeed "well north of 90%" of the time; iroh reports ~90% first-attempt hole-punch success and ~95% of data volume over direct paths. The most rigorous independent measurement, a **2025 academic campaign (arXiv:2510.27500)** covering 4.4M+ traversal attempts across 85,000+ networks in 167 countries, found **70% ± 7.1%** success for the DCUtR hole-punch stage specifically (conditional on earlier stages succeeding — ~29% of attempts never reached this stage), TCP and QUIC statistically indistinguishable (~70% each), 97.6% of successes on the first attempt. **Every one of these techniques is fundamentally UDP-based**; in a UDP-blocked, TCP-443-only environment, none of the direct-path machinery is reachable — leaving only relay-over-TCP/TLS (or TURN-over-TLS-443 as the closest UDP-firewall-surviving variant).

**Implication for tunnel design:** Treat STUN/ICE/hole-punching/DCUtR strictly as an opportunistic optimization layered on an always-available TCP/HTTPS relay (Tailscale's own architecture: connect via relay, silently attempt upgrade to direct, fall back transparently) — never the primary transport, since it depends on UDP reachability that HTTPS-only egress denies by definition.

**Sources:** [RFC 8445 (ICE)](https://www.rfc-editor.org/rfc/rfc8445.html) · [RFC 8489 (STUN)](https://www.rfc-editor.org/info/rfc8489/) · [RFC 8656 (TURN)](https://www.ietf.org/ietf-ftp/rfc/rfc8656.html) · [Tailscale: How NAT traversal works (birthday attack)](https://tailscale.com/blog/how-nat-traversal-works) · [Tailscale: NAT traversal improvements pt.1 (>90% claim)](https://tailscale.com/blog/nat-traversal-improvements-pt-1) · [libp2p DCUtR spec](https://github.com/libp2p/specs/blob/master/relay/DCUtR.md) · [arXiv:2510.27500 — "Challenging Tribal Knowledge"](https://arxiv.org/pdf/2510.27500) (4.4M attempts, 70%±7.1%) · [iroh: NAT traversal docs](https://docs.iroh.computer/concepts/nat-traversal) · [iroh blog: getting back to traversing NATs](https://www.iroh.computer/blog/iroh-0-98-0-getting-back-to-traversing-nats)

## 14. Domain fronting and ECH (Encrypted Client Hello)

Domain fronting exploited multi-tenant CDNs routing on the encrypted HTTP Host header: client sets an innocuous domain in plaintext SNI while the real destination sits in the encrypted Host header. Widely used ~2014-2018 (Tor's meek, reportedly Signal/Telegram-adjacent tooling). **Google and AWS/CloudFront both effectively killed cross-domain fronting in April 2018** by requiring front/back domains to share a customer, closing the loophole; both stated it was never an officially supported feature. **ECH**, now **RFC 9849** (published **March 2026**, closing out `draft-ietf-tls-esni`), is a different, standards-based mechanism: encrypts the entire inner ClientHello (real SNI, ALPN) under a key fetched from DNS (HTTPS/SVCB record), sending a generic outer ClientHello with a shared/non-sensitive public name in the clear. **ECH does not let a client route to an arbitrary, differently-hosted backend the way domain fronting did** — the outer name still generally identifies the CDN/operator, just not which site behind it.

**Status 2026:** Cloudflare enabled ECH by default across customer zones (initial late-2023 push globally disabled after operational issues, progressively re-enabled from August 2024). Firefox shipped ECH enabled-by-default from v118/119 (Oct 2023), fetching config via the OS resolver since v129. Chrome ramped through staged rollout from August 2023 and now ships enabled by default. Chrome/Firefox/Edge all expose enterprise policies to disable ECH (Chrome: `EncryptedClientHelloEnabled`); per the Center for Internet Security, ECH and DoH are disabled in these browsers "on a managed device" in many real deployments. Enterprise blocking in practice is not primarily DPI-level detection of the ECH extension itself (the outer ClientHello looks like ordinary TLS 1.3) — the two documented mechanisms are (1) MDM/GPO policy push disabling ECH/DoH on managed endpoints, and (2) controlling DNS so the client never obtains an ECH config: FortiGate documentation describes stripping the `ech` parameter from DoH responses, and Cisco Secure Firewall states its primary defense explicitly as "prevent clients from obtaining the ECH configuration in the first place... forcing a graceful fallback to cleartext SNI." Press coverage from late 2024 also describes Russian regulators moving to block ECH at the network level. Academic work (Niere et al., FOCI/PETS 2025) and industry analysis conclude ECH's practical circumvention value today is limited, largely because it depends on the client resolving encrypted/unblocked DNS in the first place, which a capable network operator can also interfere with.

**Implication for tunnel design:** ECH is not a substitute for or revival of domain fronting and should not be relied on as a rendezvous/evasion mechanism — it only provides SNI confidentiality that managed endpoints frequently disable via browser policy or defeat by controlling DNS/ECH-config delivery, and true cross-domain fronting has been unavailable on major CDNs since April 2018.
