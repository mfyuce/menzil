# Fact Sheet: Remote-Development Tunnels and "Unified" Access Tools

Compiled 2026-09-25. Methodology note: the session's WebSearch budget was exhausted almost immediately (shared across me and five parallel research sub-agents), so essentially every fact below was verified via WebFetch against official docs/blogs and via `gh api`/raw.githubusercontent.com reads of actual LICENSE files and source (not license badges). This is consistent with the "prefer official docs, GitHub repos, LICENSE files" instruction, but a handful of narrow sub-claims could not be independently confirmed and are flagged inline as such rather than asserted.

---

## Part 1: Remote-development tunnels

### 1. VS Code Remote Tunnels (`code tunnel`)

- **Backend**: confirmed to use Microsoft Dev Tunnels: "Tunneling securely transmits data from one network to another via Microsoft dev tunnels." [code.visualstudio.com/docs/remote/tunnels](https://code.visualstudio.com/docs/remote/tunnels)
- **Transport**: a `wss://` (WebSocket Secure, scheme-default port 443) control channel to Microsoft's Azure-hosted relay, with VS Code layering its *own* SSH-protocol encryption (AES-256-CTR) on top, since Dev Tunnels terminates TLS at the relay ingress and VS Code wants true end-to-end confidentiality. Outbound-only from the host; no inbound listeners. Same source.
- **License, the key finding**: three distinct tiers.
  1. `microsoft/vscode` ("Code - OSS") source: MIT.
  2. The official "Visual Studio Code" product/build: a separate proprietary Microsoft product license.
  3. The server/CLI component actually deployed for tunnels: governed by yet another, distinct **"Visual Studio Code Server License Terms"** ([code.visualstudio.com/license/server](https://code.visualstudio.com/license/server)), explicitly proprietary: "You may not use the software if you do not have a license for Microsoft Visual Studio Code," bars redistribution/hosting-as-a-service, and states the server is "designed for single-user access only and cannot be hosted as a service." The underlying source is the same MIT repo, but Microsoft's shipped binary is bound by these separate terms. [code.visualstudio.com/docs/remote/vscode-server](https://code.visualstudio.com/docs/remote/vscode-server) lists Remote Tunnels, Remote-SSH, Dev Containers, and Codespaces as all deploying this same component. This is a well-supported explanation for why VSCodium-style builds are refused, though no Microsoft source names "VSCodium" verbatim.
- **Port forwarding visibility**: Private (default, both ends must sign in with the same GitHub/Microsoft account) vs. Public (no sign-in required; anyone with the link can access). [code.visualstudio.com/docs/editor/port-forwarding](https://code.visualstudio.com/docs/editor/port-forwarding)
- **Documented limits** (shared Dev Tunnels account quota, resets monthly): 10 tunnels/account (oldest unused auto-deleted past that), 5 GB bandwidth/user/month, 10 ports/tunnel, 1000 active connections/port, 1500 HTTP requests/min/port, up to 20 MB/s/tunnel, 16 MB max forwarding request body. [learn.microsoft.com/azure/azure-resource-manager/management/azure-subscription-service-limits#dev-tunnels-limits](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/azure-subscription-service-limits#dev-tunnels-limits). Idle/session timeout specific to this feature is not documented (only inferable from Dev Tunnels' generic 30-day rule below).
- **HTTP proxy support**: unclear/likely incomplete. [code.visualstudio.com/docs/setup/network](https://code.visualstudio.com/docs/setup/network) states the CLI interface specifically is among the "features [that] don't yet fully support proxy networking." No `HTTPS_PROXY` confirmation found for `code tunnel`.
- **Self-hostable**: no; relies on Microsoft's hosted relay.

### 2. Microsoft Dev Tunnels (`devtunnel` CLI, standalone)

- **Status**: public preview, free, quota-limited; no pricing tier found. [learn.microsoft.com/azure/developer/dev-tunnels/overview](https://learn.microsoft.com/en-us/azure/developer/dev-tunnels/overview)
- **Quotas**: same table as above. **Tunnel lifetime**: unused tunnels auto-delete after 30 days of inactivity by default, configurable 1 hour to 30 days via `--expiration`, sliding on new activity. [learn.microsoft.com/azure/developer/dev-tunnels/faq](https://learn.microsoft.com/en-us/azure/developer/dev-tunnels/faq)
- **Anonymous access**: hosting always requires login (Entra ID/Microsoft/GitHub); "Dev tunnels doesn't support hosting tunnels anonymously." *Connecting* can be made anonymous per tunnel/port via an opt-in `--allow-anonymous` access-control entry, optionally time-limited (`devtunnel access create TUNNELID -a --expiration 2h`). [learn.microsoft.com/azure/developer/dev-tunnels/security](https://learn.microsoft.com/en-us/azure/developer/dev-tunnels/security)
- **Protocol**: WebSocket, confirmed directly from CLI output: `Connecting to host tunnel relay wss://usw2-data.rel.tunnels.api.visualstudio.com/api/v1/Host/Connect/<id>`. Minimum TLS 1.2, prefers 1.3, TLS terminated at the relay.
- **License, split exactly as suspected**: SDK/source at [github.com/microsoft/dev-tunnels](https://github.com/microsoft/dev-tunnels/blob/main/LICENSE) is MIT. The `devtunnel` CLI *binary* is bound by a separate proprietary EULA ("Microsoft Dev Tunnels Public Preview" terms, aka.ms/devtunnels/tos), which bars redistribution/hosting-as-a-service; its "only with Microsoft Visual Studio and successor products" clause reads like inherited Visual Studio boilerplate and is quoted as-is without further clarification available.
- **Self-hostable**: no.

### 3. VS Code Remote-SSH

- **ProxyCommand**: explicitly documented ("you may need to use the `ProxyCommand` parameter for your host in a local SSH config file"), and the extension consumes standard `ssh_config` syntax via `remote.SSH.configFile`. [code.visualstudio.com/docs/remote/troubleshooting](https://code.visualstudio.com/docs/remote/troubleshooting), [code.visualstudio.com/docs/remote/ssh](https://code.visualstudio.com/docs/remote/ssh)
- **ProxyJump**: not named in Microsoft's prose docs, but extensively used in practice per many issues on [github.com/microsoft/vscode-remote-release](https://github.com/microsoft/vscode-remote-release/issues) (with some Windows-specific edge-case bugs). Since ProxyJump is OpenSSH sugar for ProxyCommand and the extension parses standard config syntax, it working is expected and evidenced, just not stated verbatim by Microsoft.
- **Remote server component**: same "Visual Studio Code Server License Terms" as item 1 (single-user only, no hosting as a service). Requires outbound HTTPS/443 from the local machine to `update.code.visualstudio.com` and `vscode.download.prss.microsoft.com`.
- **Arbitrary SSH transport** (websocat/cloudflared/netcat-style ProxyCommand streams): neither confirmed nor denied by Microsoft's own docs. By OpenSSH's transport-agnostic ProxyCommand design it should work if a real sshd handshake completes over the stream, and this is independently borne out by the cloudflared and Tailscale SSH entries below (item 10), which explicitly document working with Remote-SSH-compatible `ssh` invocations.

### 4. JetBrains Gateway and Zed remote development

- **JetBrains Gateway**: SSH is the primary, named provider ("the SSH connection provider"). Other providers listed are JetBrains CodeCanvas, Gitpod, Google Cloud Workstations, Amazon CodeCatalyst, Coder, and WSL2, plus "Connect with a Link" for Code With Me; **not** JetBrains Space, and Docker is not a first-class named provider (only mentioned once, re: port forwarding into a Docker container). [jetbrains.com/help/idea/remote-development-a.html](https://www.jetbrains.com/help/idea/remote-development-a.html). License: closed-source proprietary; no public Gateway repo exists. A troubleshooting page implies a paid IDE edition is required as the remote backend ("Remote Development is available for paid versions" versus Community). Whether the Gateway *client* itself is free to download independent of that is plausible but not directly quoted anywhere official. [jetbrains.com/help/idea/remote-development-troubleshooting.html](https://www.jetbrains.com/help/idea/remote-development-troubleshooting.html)
- **Zed remote development**: local client and a remote headless `zed` server communicate over plain SSH, multiplexed through one SSH control master per project (covers the Zed protocol, terminals, and tasks). The server binary is downloaded directly by the remote machine from zed.dev by default; only with `{"upload_binary_over_ssh": true}` does the local client push the binary over SSH (for internet-restricted remotes). [zed.dev/docs/remote-development](https://zed.dev/docs/remote-development). License: repo-wide "GPL-3.0-or-later, with Apache-2.0 components where marked" (root README). The actual remote-dev server, `crates/remote_server` ("Daemon used for remote editing"), and the client-side `crates/remote` are both **GPL-3.0-or-later**, not AGPL. `crates/gpui` (UI framework) is Apache-2.0 as an example of the marked exception. `crates/collab` is currently GPL-3.0-or-later too; a historical claim that collab launched as AGPL-3.0 in 2024 could not be verified this session and should be treated as possibly outdated. [github.com/zed-industries/zed](https://github.com/zed-industries/zed) (README, `crates/remote_server/Cargo.toml`, `crates/remote/Cargo.toml`, `crates/collab/Cargo.toml`)
- Both ride plain SSH, so both compose trivially with ProxyCommand/generic stream tunnels.

### 5. code-server (Coder) and openvscode-server (Gitpod)

- **code-server**: License MIT (`github.com/coder/code-server/blob/main/LICENSE`). Its own FAQ confirms it cannot use Microsoft's marketplace per Microsoft's ToS ("Marketplace Offerings are intended for use only with Visual Studio Products and Services") and uses Open VSX instead (a legacy self-run gallery is being fully deprecated in favor of Open VSX). [github.com/coder/code-server/blob/main/docs/FAQ.md](https://github.com/coder/code-server/blob/main/docs/FAQ.md). Its own setup guide's documented exposure methods, in the order presented: (1) SSH port forwarding, their top recommendation when the host has sshd; (2) Let's Encrypt + Caddy; (3) Let's Encrypt + NGINX; (4) self-signed certificate, "a last resort"; (5) external auth via reverse proxy, naming Pomerium, oauth2-proxy, or **Cloudflare Access** (their auth product, not Cloudflare Tunnel, which is not documented by code-server itself); (6) deploy inside Coder's own platform as a `coder_app`/registry module. [github.com/coder/code-server/blob/main/docs/guide.md](https://github.com/coder/code-server/blob/main/docs/guide.md). Defaults to binding `127.0.0.1:8080` only, password-protected, rate-limited to 2 login attempts/min and 12/hour.
- **openvscode-server**: License MIT, plain and unmodified, retaining Microsoft's original copyright notice, no caveat language found (a separate `ThirdPartyNotices.txt` is just the standard vendored-dependency manifest every VS Code fork ships). [github.com/gitpod-io/openvscode-server/blob/main/LICENSE.txt](https://github.com/gitpod-io/openvscode-server/blob/main/LICENSE.txt). Open VSX is hardcoded as the default in `product.json` (`serviceUrl: https://open-vsx.org/vscode/gallery`), not just a doc recommendation. Exposure guidance is far less prescriptive than code-server's, limited to a separate docs branch of per-cloud tutorials (AWS/Azure/DigitalOcean/GCP/Railway/Render) that mostly just say "access directly at `http://<ip>:3000`." It can run with **no auth at all** by default since v1.64; `--connection-token` adds one; `--host 0.0.0.0` is required for non-localhost binding.

### 6. DevPod (loft-sh) and Coder (coder/coder)

- **DevPod**: client-agent architecture; the DevPod agent starts an SSH server using the STDIO of a provider-specific secure channel (e.g., AWS Instance Connect for AWS, `kubectl` for Kubernetes), and the local CLI/IDE forwards ports and connects over that SSH connection, literally writing `~/.ssh/config` entries (`WORKSPACE_NAME.devpod`). Its VS Code path installs **openvscode-server** in the workspace (item 5), and its JetBrains path uses Gateway over the same SSH channel. [github.com/loft-sh/devpod/blob/main/docs/pages/how-it-works/overview.mdx](https://github.com/loft-sh/devpod/blob/main/docs/pages/how-it-works/overview.mdx). Self-hosting characterization confirmed: "Client-only: No need to install a server backend, DevPod runs only on your computer," with providers pointing at infrastructure you control. "DevPod Pro" as a current hosted offering could not be confirmed: it is absent from the current docs sidebar, and `loft.sh` now redirects to `vcluster.com`, whose current product lineup does not list it, treat as a discontinuation lead, not a confirmed fact. License: **MPL-2.0** (not Apache-2.0), confirmed via the raw LICENSE file and GitHub's metadata, covering the whole repo including the Desktop app.
- **Coder**: networking is "backed by Tailscale's open source" websocket/HTTPS logic plus STUN for direct WireGuard peer discovery, but **by default Coder runs its own built-in DERP-protocol-compatible relay inside its own control plane**, not literally Tailscale's DERP servers, though it can optionally be pointed at Tailscale's real global DERP fleet or a fully custom self-hosted one. Relayed traffic rides the control plane's normal HTTPS port; geo-distributed "Workspace Proxies" are documented as needing "only port 443." [github.com/coder/coder/blob/main/docs/admin/networking/index.md](https://github.com/coder/coder/blob/main/docs/admin/networking/index.md). Self-hosting is the primary model (`coder server`, Docker, Helm, OpenShift, Rancher). License: **AGPL-3.0** core, confirmed via the LICENSE file's entire git history, exactly one commit ever (April 2022, PR #841), never changed, no relicensing event found. A separate `LICENSE.enterprise` (added September 2022, PR #3932, also unchanged) governs substantial code under `/enterprise` (audit, derpmesh, tailnet, wsproxy, scaletest, provisionerd, etc.) under a bespoke, non-SPDX, key-gated source-available license requiring Coder's Terms of Service for production use. The paid tiers are now marketed as "Premium"/"AI Premium" on `coder.com/pricing`, not "Enterprise," despite the file/directory names.

### 7. GitHub Codespaces and Gitpod

- **Codespaces**: fully closed/hosted SaaS with no self-host path (docs describe it as "hosted by GitHub in a Docker container," with only limited access to the outer VM). Forwarded-port URL pattern: `https://<codespace-name>-<port>.app.github.dev`, private by default, switchable to "Private to Organization" or "Public." [docs.github.com/en/codespaces/developing-in-a-codespace/forwarding-ports-in-your-codespace](https://docs.github.com/en/codespaces/developing-in-a-codespace/forwarding-ports-in-your-codespace)
- **Gitpod, major update**: Gitpod has been renamed **"Ona"** and, per a June 11, 2026 blog post ("Ona is joining OpenAI"), is now part of OpenAI. `gitpod.io` 308-redirects to `ona.com`; the GitHub repo banner reads "Gitpod has been renamed to Ona"; "Gitpod Classic pay-as-you-go did sunset on October 15th 2025." [github.com/gitpod-io/gitpod](https://github.com/gitpod-io/gitpod), [ona.com/blog](https://ona.com/blog). The current architecture is a hybrid: the management/coordination plane is SaaS-only, not self-hostable, while "Runners" (the execution layer) can run on Ona Cloud or on customer infrastructure (AWS/GCP), i.e. self-hostable runners with a SaaS-only control plane. [ona.com/docs/ona/understanding/architecture.md](https://ona.com/docs/ona/understanding/architecture.md). "Gitpod Flex" as an official product name could not be confirmed in current docs; treat as unverified. Port forwarding: Classic used `<port>-<workspace-name>.ws-<region>.gitpod.io`, private by default; the current Ona product documents automatic-TLS HTTPS URLs without a confirmed exact hostname pattern, private-to-creator by default, wideneable to organization or everyone.

### 8. Terminal sharing: sshx, upterm, tmate

- **sshx** (ekzhang/sshx): transport is **not** WebSocket-only as commonly assumed; it is gRPC over HTTP/2 between the `sshx` CLI and the relay server, plus WebSocket for the browser viewer. Default server port **8051** (localhost by default). **Self-hosting is explicitly not officially supported**: "Self-hosted deployments are not supported at the moment. If you want to deploy sshx, you'll need to properly implement HTTP/TCP reverse proxies, gRPC forwarding, TLS termination, private mesh networking, and graceful shutdown." [raw.githubusercontent.com/ekzhang/sshx/main/README.md](https://raw.githubusercontent.com/ekzhang/sshx/main/README.md). License: MIT.
- **upterm** (owenthereal): host machine runs an SSH server and opens a reverse SSH tunnel to a relay (`uptermd`); clients connect via "ssh or ssh over WebSocket" (e.g., `ssh TOKEN@uptermd.upterm.dev`). Self-hostable, confirmed by concrete deployment artifacts in the repo (`Dockerfile.uptermd`, Heroku `Procfile`, `fly.toml`, Helm charts, systemd units, Terraform). License: Apache-2.0.
- **tmate**: the client is a tmux fork statically linked with libssh (`configure.ac` requires libssh >= 0.8.4). Self-hosting repo names differ from common assumption: the actual components are **`tmate-ssh-server`** (the SSH daemon) and **`tmate-websocket`** (browser/HTML5 access), not "tmate-server," which does not exist as a repo (404). License is genuinely split and messy: the client's README says "BSD-licensed" but the actual `COPYING` is per-file ISC-style text inherited from tmux, and GitHub's detector reports "NOASSERTION"; `tmate-ssh-server`'s README says "MIT license" but has no machine-readable LICENSE file either (also NOASSERTION on GitHub). tmate.io itself was unreachable (DNS failure) during research; all findings are GitHub-sourced.

### 9. wush, ShellHub, Apache Guacamole, RustDesk, mosh, Eternal Terminal (Teleport: see Part 2)

- **Coder's wush**: peer-to-peer CLI for file transfer (`wush cp`) and remote shell (`wush ssh`/`wush serve`), built on Tailscale's open-source `tsnet` package, using "an in-memory control server on each CLI" instead of a persistent coordinator; no Tailscale account required. Transport is direct UDP via NAT hole-punching, falling back to DERP relay, on dynamic/ephemeral ports (no fixed port documented). **Self-hosting the DERP relay is not supported**: "We utilize Tailscale's public DERP relays, but no Tailscale account is required," with no self-hosted-relay flag found. License: **CC0-1.0** (public-domain-style), confirmed from the raw LICENSE file, an unusual choice worth double-checking if decision-relevant. [github.com/coder/wush](https://github.com/coder/wush)
- **ShellHub**: agents on each device dial out to the ShellHub server over a secure WebSocket (outbound, NAT-friendly). Users connect via a web UI or standard SSH client tools with device-scoped syntax (`ssh user@demo.device-1@cloud.shellhub.io`); also supports SCP/SFTP, SSH port forwarding, and a SOCKS proxy. Exact numeric port for the SSH-facing listener was not found verbatim. Self-hostable Community Edition (Apache-2.0, not AGPL, confirmed via GitHub's license API on `LICENSE.md`), with Enterprise (self-hosted or managed) and Cloud (SaaS) editions gated by configuration/deployment files rather than a second license file. [docs.shellhub.io](https://docs.shellhub.io/overview/editions)
- **Apache Guacamole**: browser to JS client to web app over HTTP(S)/WebSocket, web app forwards the Guacamole protocol over plain TCP to `guacd` (default port **4822**), which speaks RDP (FreeRDP), VNC (libVNCserver), SSH (libssh2), or Telnet (libtelnet) onward to the target. HTTPS is documented and recommended (typically via reverse-proxy SSL termination) but not enforced by Guacamole itself. Fully self-hostable (Apache Software Foundation project). License: Apache-2.0 for both `guacamole-server` and `guacamole-client`, confirmed against the actual LICENSE files. [guacamole.apache.org/doc/gug/guacamole-architecture.html](https://guacamole.apache.org/doc/gug/guacamole-architecture.html)
- **RustDesk**: `hbbs` listens on TCP 21115/21116/21118 plus UDP 21116 (plus TCP 21114 for the Pro-only HTTP API); `hbbr` listens on TCP 21117/21119 (WebSocket). Minimum OSS deployment needs TCP 21115 to 21117 plus UDP 21116. [rustdesk.com/docs/en/self-host/](https://rustdesk.com/docs/en/self-host/). License: **AGPL-3.0** for both `rustdesk` (client; the license file is literally named `LICENCE`) and `rustdesk-server`, confirmed against the actual files. Open-core structure confirmed at the product level: "RustDesk Server Pro" is sold commercially (from $11.88/month); a public `rustdesk-server-pro` repo exists but only contains deployment scripts, the Pro binary/source itself stays closed. A narrower claim that specific plugins are closed-source Pro-only was not found/confirmed.
- **mosh**: SSH is used only for the initial handshake, exchanging an AES-128 key and a UDP port before the SSH connection closes; the session itself runs entirely over UDP, default port range **60000 to 61000** (configurable via `-p`). License: **GPL-3.0-or-later** (the `COPYING` file is plain GPLv3 text, but source file headers carry the "or later" grant plus an OpenSSL-linking exception), more precise than GitHub's own license badge.
- **Eternal Terminal**: three binaries (`et` client, `etterminal` per-user server helper, `etserver` daemon). SSH is used only for the initial auth/launch handshake, like mosh, but the persistent, reconnectable session itself runs over ET's own TCP protocol on default port **TCP 2022** (configurable), not UDP: "ET uses TCP, so you need an open port on your server." License: Apache-2.0.

### 10. cloudflared "access ssh"/"access tcp" and Tailscale SSH

- **cloudflared**: `cloudflared` on the origin opens an outbound-only connection to Cloudflare's edge, no inbound ports needed. [developers.cloudflare.com/cloudflare-one/connections/connect-networks/](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/). The ProxyCommand pattern is documented with this exact config:
  ```
  Host ssh.example.com
  ProxyCommand /usr/local/bin/cloudflared access ssh --hostname %h
  ```
  followed by plain `ssh user@ssh.example.com` (cloudflared opens a browser for identity-provider auth, then proxies over HTTPS through Cloudflare's edge). [developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/use-cases/ssh/ssh-cloudflared-authentication/](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/use-cases/ssh/ssh-cloudflared-authentication/). VS Code Remote-SSH using this specific pattern is not named in any official Cloudflare source found (checked the full docs index); the mechanism itself (standard `ProxyCommand` in `ssh_config`) is exactly what Remote-SSH is independently documented to honor (item 3), so it should work, but no Cloudflare-owned confirmation exists. License: Apache-2.0, confirmed as complete, unmodified standard text with no supplementary NOTICE terms.
- **Tailscale SSH**: `tailscaled` claims port 22 on the Tailscale IP and routes SSH traffic to Tailscale's own SSH server rather than any configured system sshd, authenticating and encrypting over WireGuard using Tailscale node keys; the SSH protocol's authentication phase is short-circuited because the Tailscale SSH server already knows the peer's identity. Authorization is governed by the tailnet policy file (ACL grants), not per-host `authorized_keys`. [tailscale.com/kb/1193/tailscale-ssh](https://tailscale.com/kb/1193/tailscale-ssh). Plain `ssh user@100.x.y.z` is documented to work "without any new binary or configuration file," and Tailscale implements SFTP (needed for VS Code Server's own deployment mechanism), strongly supporting "Remote-SSH just works," though no official Tailscale source names "VS Code"/"Remote-SSH" explicitly. Documented limitations: fixed to port 22 (not configurable), unsupported on Synology/QNAP, restarting `tailscaled` drops sessions, and an optional "check mode" ACL can force periodic browser re-auth (default 12 hour period) that could interrupt long-lived connections. A specific claim that port-forwarding/tunneling is separately ACL-gated could not be confirmed or denied (zero hits searching the KB page). License: `tailscale/tailscale` is **BSD-3-Clause** (client/`tailscaled`/CLI, confirmed open source), while the coordination/control-plane server is closed-source SaaS: "Tailscale's own hosted coordination server remains proprietary as part of our managed service." [tailscale.com/opensource](https://tailscale.com/opensource). **headscale** ([github.com/juanfont/headscale](https://github.com/juanfont/headscale)) is BSD-3-Clause, an "independent, community-maintained" reimplementation "developed independently and separately from Tailscale," though Tailscale employs/supports its maintainer.

## Part 2: "Unified" attempts (public share + private reach-in + egress/VPN)

### zrok (openziti/zrok)

- **Public share**: `zrok share public localhost:8080` creates a public HTTPS URL; limited to HTTP/HTTPS-reachable resources.
- **Private share**: `zrok share private localhost:3000`, peer-to-peer, requires the accessing user to have a zrok account on the same instance (`zrok enable`) and the share token; no firewall ports opened; access ends the instant the sharing process terminates. [github.com/openziti/zrok](https://github.com/openziti/zrok) (`website/docs/concepts/private-shares.mdx`)
- **Drive share**: converts a local directory into a shareable, browsable network drive (`--backend-mode drive`).
- **SOCKS/VPN**: zrok currently ships a **`socks` backend mode** (added v0.4.24, still current and documented): `zrok share private --backend-mode socks` plus `zrok access private --bind 127.0.0.1:1080 <token>` yields a local SOCKS5 proxy for dynamic port forwarding to multiple destinations, described in the changelog as "very lightweight VPN-like functionality." A separate, fuller **`vpn` backend mode** (TUN-device based, added v0.4.27) was later **removed in v1.1.11** "due to dependency management issues... the underlying TUN device libraries created conflicts," with a migration guide provided. [CHANGELOG.md](https://github.com/openziti/zrok/blob/main/CHANGELOG.md), [website/docs/how-tos/shares/socks-proxy-mode.mdx](https://github.com/openziti/zrok/blob/main/website/docs/how-tos/shares/socks-proxy-mode.mdx)
- Built on **OpenZiti**, a "programmable zero-trust network overlay" enabling firewall/NAT traversal without inbound connectivity.
- License: **Apache-2.0**. Self-host: fully self-hostable, "from Raspberry Pi to enterprise scale," single binary, or use the free hosted zrok.io service.
- **Capabilities**: public share yes, private reach-in yes, egress (SOCKS) yes currently, full VPN no (removed).

### Pangolin (fosrl/pangolin)

- **Sites via newt**: a WireGuard-based agent providing "outbound tunnels and intelligent NAT traversal" into a network, requiring no open ports or public IP on the site.
- **Traefik**: powers the reverse-proxy layer for HTTPS web app exposure and browser-based VNC/RDP/SSH.
- **Identity/SSO**: bring-your-own identity provider or built-in Pangolin identities, RBAC, audit logging, SSO/OIDC.
- **Clients**: "peer-to-peer with intelligent NAT traversal" for private access to SSH servers, databases, RDP, and network ranges, a mesh-VPN-like private reach-in capability confirmed current in the repo README.
- **Egress/VPN**: not found or documented; the project appears scoped to application-specific and private-network access, not general internet-egress routing.
- License: **dual AGPL-3.0 / "Fossorial Commercial License"** (company: Fossorial, Inc.), confirmed by reading the raw LICENSE file directly: files with a commercial-license header are commercial-only, AGPL-licensed files remain available under the commercial license by written agreement, and files with no header default to AGPL-3.0. Language: TypeScript/Node.js. Self-host: designed for Docker Compose self-hosting.
- **Capabilities**: public share yes (via Traefik), private reach-in yes (identity-gated plus client mesh), egress VPN not found/likely absent.

### inlets (inlets/inlets, inlets-pro)

- **Major finding**: the original free, MIT-licensed `inlets` OSS repo no longer exists at `github.com/inlets/inlets` (confirmed 404). The `inlets` GitHub org's current repos are `inlets-pro`, `agent-skills`, `docs.inlets.dev`, `inlets-operator`, `inletsctl`, `mixctl`, `inlets.dev`, `cloud-provision`, `ingress-example`, `inlets-svc`, and `media`, with no plain OSS `inlets` repo remaining.
- `inlets-pro` is now fully commercial: "A valid license key or Gumroad subscription is required to launch or deploy inlets," under an EULA from OpenFaaS Ltd (UK company no. 11076587): "inlets Pro is licensed as commercial software and must not be used without a valid license key." No OSS license is detected on the repo (GitHub's license API returns 404).
- Mechanism: a self-run "exit server" (e.g., a cheap VPS) plus an inlets client on the NAT'd machine, one binary containing both roles, works bare-metal/VM/container/Kubernetes. The project's own positioning: "Inlets is not a VPN, it's for exposing local services on another network or on the Internet."
- **Capabilities**: public share yes (its core purpose), private reach-in only via auth tokens (not deeply verified), egress/VPN explicitly disclaimed by the project itself, missing. Self-host: the exit server is always self-run by the user; no hosted-exit-server-as-a-service was found.

### boringproxy (boringproxy/boringproxy)

- Mechanism: a self-hosted, single-binary Go tunnel server and client with its own reverse proxy and ACME/Let's Encrypt TLS provisioning for public HTTPS URLs.
- License: MIT, confirmed via GitHub's license API.
- Self-host: always self-hosted, no vendor SaaS option.
- **Maintenance status, checked live**: last tagged release **v0.10.0**, published 2023-01-04; most recent visible commit 2023-05-17; 60 open issues; not formally archived but shows no meaningful activity in roughly two and a half years as of September 2026, reasonably characterized as dormant/unmaintained. [github.com/boringproxy/boringproxy](https://github.com/boringproxy/boringproxy)
- **Capabilities**: public share yes, private reach-in and egress/VPN not documented, effectively missing.

### Tailscale (Funnel + Serve + exit nodes + SSH): the fullest unified picture found

- **Funnel** (public share): exposes a local service publicly at `https://<machine>.<tailnet>.ts.net`. Restricted to exactly ports **443, 8443, and 10000** ("Funnel can only listen on ports 443, 8443, and 10000"), available on **all plans including free**, with non-configurable bandwidth caps, TLS-only, and the same port cannot be used for both Serve and Funnel simultaneously. [tailscale.com/kb/1223/funnel](https://tailscale.com/kb/1223/funnel)
- **Serve** (private reach-in): serves a local service only to your own tailnet devices, never the public internet.
- **Exit nodes** (egress VPN): routes a device's general internet traffic through another tailnet device, WireGuard-based.
- **Transport for restrictive networks**: confirmed directly, "Connections to the coordination server and other backend systems and data connections to the DERP relays use HTTPS on port 443." Also: UDP 41641 for direct WireGuard peer-to-peer (reconfigurable), UDP 3478 for STUN, and TCP 80 for HTTP coordination fallback/captive-portal detection. [tailscale.com/kb/1082/firewall-ports](https://tailscale.com/kb/1082/firewall-ports). Explicit corporate `HTTP_PROXY` support was not confirmed in the pages checked (unconfirmed, not denied).
- License: client (`tailscale/tailscale`, including `tailscaled` and the CLI) is **BSD-3-Clause** and confirmed open source; the coordination/control-plane server is closed-source SaaS ("Tailscale's own hosted coordination server remains proprietary as part of our managed service"). [tailscale.com/opensource](https://tailscale.com/opensource). **headscale** is the unofficial, BSD-3-Clause, community-maintained self-hosted alternative control server.
- **Capabilities**: public share yes (Funnel), private reach-in yes (Serve plus SSH plus general tailnet access), egress VPN yes (exit nodes). The only tool researched that clearly covers all three.

### NetBird (netbirdio/netbird)

- **Exit nodes/egress**: confirmed yes. "Routes also power exit nodes: a default route (0.0.0.0/0) that sends all internet traffic from peers in its distribution groups through a routing peer," which performs NAT by default. [docs.netbird.io](https://docs.netbird.io/how-to/routing-traffic-to-private-networks)
- **Public exposure**: no equivalent to Tailscale Funnel was found; NetBird's own docs focus exclusively on private mesh networking and access-control policies, reasonably characterized as private-mesh-only for public sharing.
- **License, precisely confirmed by reading the raw LICENSE file**: "This BSD-3-Clause license applies to all parts of the repository except for the directories management/, signal/, relay/ and combined/. Those directories are licensed under the GNU Affero General Public License version 3.0 (AGPLv3)." So the client/agent is BSD-3-Clause, but the self-hosted **server** components (management, signal, and relay servers) are **AGPL-3.0**, confirmed also by a `LICENSES/` directory containing both full license texts plus a `REUSE.toml`. [github.com/netbirdio/netbird/blob/main/LICENSE](https://github.com/netbirdio/netbird/blob/main/LICENSE)
- Self-host: a single install script generates a "full, production-ready" Docker Compose stack (management, signal, relay, STUN); the VM needs TCP 80/443 and UDP 3478 publicly reachable. Whether relay traffic itself can additionally ride TCP 443 for fully restrictive networks was not confirmed either way.
- **Capabilities**: public share no/not found, private reach-in yes, egress VPN yes.

### Firezone (firezone/firezone)

- **Resources and Gateways**: Resources are DNS patterns, individual IPs, CIDR ranges, or Device Pools; Gateways serve specific Resources within a Site ("Resources must be reachable by all Gateways in the same Site").
- **Public share**: none found; access is entirely policy-based and requires administrative configuration, no anonymous sharing capability.
- **Egress VPN**: confirmed yes, via the **"Internet Resource"** feature, available on paid plans, routing 0.0.0.0/0 and ::/0 through designated Gateways as a fallback for unmatched traffic, with Gateways serving it explicitly rejecting private-range (RFC 1918 etc.) traffic to prevent internal-resource leakage. [firezone.dev/kb/deploy/resources](https://www.firezone.dev/kb/deploy/resources)
- Transport: WireGuard data plane plus STUN/TURN-like relays for NAT traversal; whether relay traffic can run over 443 specifically was not confirmed in the pages checked.
- License: **Apache-2.0**, a single LICENSE file at the repo root with no separate open-core license-file split found (unlike Pangolin/NetBird), though the paid-plan gating of the Internet Resource feature suggests some form of feature/hosting-based tiering exists even without a second license file.
- Self-host: multiple deployment options, Docker Compose, hardened systemd service, APT repo, direct binary, or infrastructure-as-code for AWS/GCP/Azure.
- **Capabilities**: public share no, private reach-in yes (its core purpose), egress VPN yes (paid feature).

### Teleport (gravitational/teleport)

- **Architecture**: agent processes dial outbound to a central Proxy/Auth service (reverse tunnel), so no inbound ports are needed on protected resources; a single deployment mediates SSH, Kubernetes, database, and internal-app access uniformly.
- **License history, precisely confirmed via the LICENSE file's complete git commit history** (only two commits ever touch that path):
  - 2015-10-31: "Apply apache license to teleport" (originally Apache-2.0).
  - **2023-12-01: "Updated Teleport codebase to AGPL3 license (#35259)"**, commit `b178b8b7`. The current LICENSE file is plain, undecorated AGPL-3.0 text.
  [github.com/gravitational/teleport, commit history for path LICENSE](https://github.com/gravitational/teleport/commits/master/LICENSE)
  - Enterprise code is **not** in this public repo at all; it lives in a separate git **submodule** at path `e` (confirmed via the GitHub API reporting `"type": "submodule"`), meaning Teleport's open-core split is architectural (a separate, presumably private submodule) rather than same-repo dual-licensed files as with Pangolin or NetBird.
- **Capability classification**: primarily private reach-in / identity-based access management. Not a public-anonymous-share tool and not a general egress VPN/SOCKS tool.
- Self-host: Community Edition (AGPL-3.0) is self-hostable; Teleport Enterprise Cloud is the hosted option. Exact current default ports (historically 3080 web/API, 3023/3024 SSH proxy/tunnel, 3025 auth, with recent versions trending toward multiplexing over a single port) were not independently re-verified against the latest docs in this pass and should be treated as general background rather than freshly confirmed.
- **Capabilities**: public share no, private reach-in yes, egress VPN no.
